Mocks Built with the Same Principles They Test

The mock builder is itself an application of the principles the exam tests. The same patterns you are expected to recognise and apply are built into the system that generates the questions. So the mocks are more than practice. They are a working example of the exam’s principles in action. Each step below traces those principles back to the relevant task statements, while showing where the design failed, what we learned, and how the system improved.

Overview · 30 seconds

A failed question goes back to the writer with its findings

A question that fails step 3 or step 4 goes back to the writer, with the failed question and the exact findings. The new try goes through steps 3 and 4 again. This is the one automatic loop of the mock builder. A question that passes stops the loop.

Explanation

3 minutes

What the writer gets. The request of step 2, the failed try and its findings. A finding names the rule and the letter of the option. The writer does not see older tries, so the request stays short. The guide names the same three parts for a new try: the original, the failed result and the errors (4.4-S1).

The limits. Each start of a slot has at most 3 tries, and 2 results “cannot decide” also stop it. Code checks for a pass first, so the limits are only guards. A slot that reaches a limit waits for the owner. The other slots continue.

The record. Each try is a new file. No file is written over, so the history of each question stays.

Depth

what went wrong, and the fix

The review loop that ended when the control became code

The answer to each review added rules, and the new rules made new cases. The fix: one automatic loop. Each other failure waits for the owner. The control became code, with tests that make no model call. Code checks for a pass before the limits. Today the program has 228 tests.

The reason of the owner reached only one try

Slot M5-S38 failed rule B9 three times. The owner gave more tries with a reason: “B9 failed three times on the problem of resubmitting failed requests. Use the second problem of the point instead: custom_id to match each answer to its request, because batch results do not come back in the order of the requests.” But the program sent the writer only the last failed try and its findings, not the reason. So mock decision 0074 added the reason to the next request, in the code, and a test checks it.

The run files show more. Try 4 got the reason and followed it: its correct options use custom_id. It failed B9, because question M1-S46 of mock 1 had the same problem. Try 5 did not get the reason. In the code, the branch for a failed try of the start runs before the fix, and the test checks only the first try after the decision. Try 5 wrote the old problem again: “resubmits every request instead of only the failed ones”. It passed, and it is the question in mock 5. Mock decision 0074 says: “The instruction reached the writer, but the question did not follow it.” The run files show that only one try got the instruction. A test shows that a case has a path. It does not show that the path is good.
