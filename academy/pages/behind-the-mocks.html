Exam guide breakdownBehind the mocks

Mocks Built with the Same Principles They Test

The mock builder is itself an application of the principles the exam tests. The same patterns you are expected to recognise and apply are built into the system that generates the questions. So the mocks are more than practice. They are a working example of the exam’s principles in action. Each step below traces those principles back to the relevant task statements, while showing where the design failed, what we learned, and how the system improved.

Prepare the guide records

code · task statements 1.3, 5.6

Overview · 30 seconds

A script copies the exam guide into records, once

Before the first mock, a script copies the parts of the exam guide that the later steps need into one file of records. No model copies text. It runs once for each version of the guide, not once for each mock. The file has the 5 domains, 6 scenarios, 30 task statements, 240 points and 12 sample questions of the guide. A later step takes the parts that it needs from the file, by ID.

Explanation

3 minutes

IDs. Each point gets an ID that the guide does not have: the task statement, then K (Knowledge of) or S (Skills in), then the number of the bullet. So 1.4-K2 is the second “Knowledge of” bullet of task statement 1.4. Every question of the 5 mocks keeps the ID of its point: 300 of 300.

Checks. The script leaves out the 39 page headers of the PDF, so that no list is cut in two. It checks the counts and that each text is exactly in the guide, or it writes no file. Then three checks:

  1. A second script, which does not use the code of step 0, checks the file: 41 of 41 checks pass.
  2. An independent reviewer wrote its own script, compared the records with the guide record by record, and found no errors.
  3. On 13 October 2026, a script compared the copy of the guide with the official PDF, word for word: 0 differences.

The task statements that step 0 uses

Task statement 1.3 Configure subagent invocation, context passing, and spawning Exam guide breakdown 1.3 →
Task statement 5.6 Preserve information provenance and handle uncertainty in multi-source synthesis Exam guide breakdown 5.6 →

Depth

what went wrong, and the fix

The design started at step 1, and a proposal had no source

Early in the design, a proposal for step 2 said “the story of the scenario” and “a fixed form with fields”. It had no source for the story and no fields. The cause: the plan of work started at step 1, but each step reads the records of step 0. The fix: step 0 was designed and run before step 2, and each design names the exact file format and fields. Working rule 30 has the same words: each design proposal names the exact file format and the exact fields.

One more correction came earlier. The assistant suggested to call this work an input, not a step. The owner said that it must be documented, because a goal of the build is a record that a portal page can show. So step 0 has a number, a decision and a box in Fig. A.

No source records a failure of the script or of the file. The file has not changed since the first commit of the repository, on 7 October 2026.

Plan the mock

code · task statements 1.4, 1.6

Overview · 30 seconds

Code plans all 60 questions before a model writes one

Before a model writes a question, code makes the plan of the mock: a list of 60 slots. Each slot says what one question must be: the scenario, the task statement, one point, the question type and the number of answers. The counts of a mock must hold each time, and a model that makes the plan can make an error in a count.

Explanation

3 minutes

The counts. A mock has 4 scenarios of 15 questions, and 16, 11, 12, 12, 9 questions for domains 1 to 5. The weights of the guide give the domain counts. Each slot gets one point of its task statement. An idea is a group of points of the guide on one subject: the build put the 240 points into 95 ideas. No two slots of one mock get points of the same idea.

Depth

what went wrong, and the fix

Mock 1 repeated itself, so the plan learned the ideas

Mock 1 had questions that repeated each other. Most repeats came from two points of the guide on one idea. So the build grouped the 240 points into 95 ideas, and code now stops a plan with two slots on one idea. The plan is code, so code can prevent this before any question is written.

The first version of the rule could never make a plan: a script ran it over 2000 seeds, and each seed failed. The fix gave a task statement no more questions than its number of ideas. “So the count must follow the groups, not the groups the count.” An independent review of that code then found a bug: the code could stop although a plan existed.

Mock 2 repeated mock 1

Before mock 2, the owner asked: “Is there no simple way to ensure that similar questions are spread out between mocks?” So step 1 reads the built earlier mocks, and it puts the least-used ideas first. That spread the ideas, but it did not prevent the same question in two mocks. A second review found that 17 questions of mock 2 repeat mock 1. Part of the cause was in step 1: 7 slots of mock 2 had the same point as mock 1, although their idea had a point that mock 1 did not use. So now inside an idea, the point that earlier mocks used less comes first. Step 2 got the earlier questions on the idea, and step 4 got rule B9. Over the 5 built mocks, 84 of the 95 ideas are in 2 to 4 mocks.

Write the question

a Claude model · task statements 4.3, 4.2, 4.1, 1.4

Overview · 30 seconds

One new Claude call writes each question, from a request that code builds

For each slot of the plan, one call of the Claude API writes one question. The call is new each time, and it does not know the other questions of the mock. One call makes one record, so each later verdict connects to exactly one question, and a failed question is written again alone. Code builds the request from the guide records and the plan, and code, not the model, mixes the options and gives the letters.

Explanation

3 minutes

The rules come first. From mock 4, the list of rules is a separate first block with a cache mark, so a repeated list costs less (mock decision 0067). The writer gets the 21 rules that steps 3 and 4 check, so each of them is also checked. Two other instructions to the writer have no check. Each of the 488 tries of the 5 mocks used claude-opus-5-5.

The form. The writer answers in a fixed form: the question, and each option with a mark (correct or wrong) and a reason. It can also answer “cannot write”. Claude Opus 5.5, the model of this build, and three other current models (Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1) reject a forced tool call, so the build sends its form as structured outputs. For the exam: the guide's answer for a fixed form is tool use with a JSON schema (4.3-K1). It names tool_choice "any" when several schemas exist and the document type is unknown (4.3-S2), and a forced tool when one extraction must run first (4.3-S3).

The letters. In the 12 sample questions of the guide, the correct answer is A 10 times and B 2 times, and a model can copy that (an assumption, not checked). So code mixes the options and gives the letters. From mock 5, the correct options take the letters that the plan sets.

The cost of one call per slot. The writer sees one slot, so it cannot see the other questions of its scenario. Step 6 checks the questions of a scenario together.

Depth

what went wrong, and the fix

The writer did not know the earlier mocks

In mock 2, the writer did not know mock 1. On a shared idea it wrote the most obvious scene again, often with the same wrong options. Example on one idea, the stop of an agentic loop:

  1. Mock 1, M1-S28: the correct answer checks stop_reason and continues while it is “tool_use”.
  2. Mock 2, M2-S08, try 1: the correct answer again continues while stop_reason is “tool_use”.

The owner sent it back: “Use a different scene and a different angle: the cause, the fix, or a choice between rules.” The new try asked for the cause instead: a fixed cap of 12 iterations as the main stopping rule.

The fix for step 2: when the idea of a slot is in an earlier mock, the writer gets the earlier questions on that idea, with the mark of each option. In the same mock decision, step 4 got rule B9 to check it.

The first bad mark became an instruction and a check

In the first test of the writer, the owner marked one question bad: “The question is confusing and needs calrification. I had to read the question more than one time.” The assistant first suggested an instruction only. The owner asked: “but is that enough? Only in the prompt?” So the writer got the instruction “Use one name for one actor”, and because of that question, step 4 got rule B7 to check it.

The design forced a tool call

The first design said that the request forces the model to call a tool. Before the code was written, the documentation showed that the newest models reject it. So the build chose structured outputs: a JSON schema in each request. The code never had a forced tool call, and a test checks that the shared model call sends no tool and no tool choice.

Check by code

code · task statements 1.4, 4.3, 4.4, 5.3

Overview · 30 seconds

Code checks 12 exact rules before a model sees the question

Code checks each try against 12 rules that have one exact answer, such as the number of options and the length of the text. The check is cheap and fast, so a question with a simple defect does not use a model call. In mocks 1 to 5, 477 of 488 tries passed, and 11 failed.

Explanation

3 minutes

Code or a model. Code checks a rule that has one correct answer, and a model checks a rule that needs judgment. A model checks the rules that need judgment in step 4.

Why the form does not count. The writer answers in a fixed form, but a JSON schema for structured outputs cannot limit the number of items in a list, beyond a minimum of 0 or 1. The writer is told the number of options in words only. So the design does not rely on the form for a count: step 3 counts the options and the correct answers.

what went wrong, and the fix

The writer wrote 6 options for a slot of 5

Twice the writer was told to write 5 options and wrote 6: M4-S27-T3 and M5-S60-T2. In M4-S27, try 3, the sixth option was F. The form could not stop it. Rule A2 failed both tries, and the writer tried again. The owner noted it: “The last try failed on the form (rules A1 and A2), not on B9.”

The longest option was too often correct

In the built mock 1, the correct option was the longest in 37 of the 52 one-answer questions. Chance is 13. Each question passed rule A7, which looks at one question only. The build did not choose a rule that the correct option is never the longest: then a participant learns that the longest option is always wrong. Instead, a participant who always selects the longest option must not gain from it. So step 1 marks 13 of the 52 one-answer slots where the longest option may be correct, and rule A12 fails a question where a correct option is the longest on any other slot.

Try again

a Claude model: the writer of step 2 again, with the failed try and its findings · task statements 4.4, 1.1, 4.3

Overview · 30 seconds

A failed try goes back to the writer with its findings

A question that fails step 3 or step 4 goes back to the writer, with the failed try and its exact findings. The new try goes through steps 3 and 4 again. This is the one automatic loop of the mock builder. A question that passes stops the loop.

Explanation

3 minutes

What the writer gets. The request of step 2, the failed try and its findings. A finding names the rule and, where it fits, the letter of the option. The writer does not see older tries, so the request stays short. The exam guide names the same three parts for a new try: the original, the failed result and the errors (point 4.4-S1 of the exam guide).

The limits. Each start of a slot has at most 3 tries. 2 results “cannot decide” of step 4 also stop it. A start is the first try of a slot, or the first try after a decision of the owner. The other slots continue.

The record. Each try is a new file. No file is written over, so the history of each question stays.

The task statements that step 5 uses

Task statement 1.1 Design and implement agentic loops for autonomous task execution Exam guide breakdown 1.1 →

Depth

what went wrong, and the fix

The review loop that ended when the rules became code

The fix kept one automatic loop. Each other failure waits for the owner. The rules of the next action became code, with tests that make no model call. Now the code that moves each try checks for a pass before the limits. Today the mock builder has 228 tests.

The reason of the owner reached only one try

Slot M5-S38 failed rule B9 of step 4 (a question must not repeat the problem of an earlier question) three times. The owner gave more tries with a reason: “B9 failed three times on the problem of resubmitting failed requests. Use the second problem of the point instead: custom_id to match each answer to its request, because batch results do not come back in the order of the requests.” But the mock builder, as it was built, sent the writer only the last failed try and its findings, not the reason. So mock decision 0074 (a decision record of the build) added the reason to the next request, in the code, and a test checks it.

The run files and the code show more. Try 4 got the reason and put a custom ID into its correct options: “Select the files to resubmit by reading the custom_id of each failed result…” It failed B9, because it repeated questions of mock 1 (M1-S46) and mock 3 (M3-S12). Try 2, before the reason, had already tried a custom ID and failed B9 on the same question of mock 1. Try 5 did not get the reason. In the code, the branch for a failed try of the start runs before the fix, and the test checks only the first try after the decision. Try 5 wrote the old problem again: “resubmits every request instead of only the failed ones”. It passed, and it is the question in mock 5. Mock decision 0074 says: “The instruction reached the writer, but the question did not follow it.” The code shows that only the first try of the new start got the instruction. The code still works this way. A test shows that a case has a path. It does not show that the path is good.
