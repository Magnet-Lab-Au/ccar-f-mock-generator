Exam guide breakdownBehind the mocks

Mocks Built with the Same Principles They Test

The mock builder is itself an application of the principles the exam tests. The same patterns you are expected to recognise and apply are built into the system that generates the questions. So the mocks are more than practice. They are a working example of the exam’s principles in action. Each step below traces those principles back to the relevant task statements, while showing where the design failed, what we learned, and how the system improved.

Prepare the guide records

code · task statements 1.3, 5.6

Overview · 30 seconds

A script copies the exam guide into records, once

Before the first mock, a script copies the parts of the exam guide that the later steps need into one file of records. No model copies text. It runs once for each version of the guide, not once for each mock. The file has the 5 domains, 6 scenarios, 30 task statements, 240 points and 12 sample questions of the guide. A later step takes the parts that it needs from the file, by ID.

Explanation

3 minutes

Labels. Each point gets a label that the guide does not have: the task statement, then K (Knowledge of) or S (Skills in), then the number of the bullet. So 1.4-K2 is the second “Knowledge of” bullet of task statement 1.4. Every question of the 5 mocks keeps the ID of its point: 300 of 300.

Checks. The script leaves out the 39 page headers of the PDF, so that no list is cut in two. It checks the counts and that each text is exactly in the guide, or it writes no file. Then three checks:

  1. A second script, which does not use the code of step 0, checks the file: 41 of 41 checks pass.
  2. An independent reviewer wrote its own script, compared the records with the guide record by record, and found no errors.
  3. On 13 October 2026, a script compared the copy of the guide with the official PDF, word for word: 0 differences.

Task statement 1.3 Configure subagent invocation, context passing, and spawning Exam guide breakdown 1.3 →
Task statement 5.6 Preserve information provenance and handle uncertainty in multi-source synthesis Exam guide breakdown 5.6 →

One more correction came earlier. The assistant suggested to call this work an input, not a step. The owner said that it must be documented, because a goal of the build is a record that a portal page can show. So step 0 has a number, a decision and a box in Fig. A.

No source records a failure of the script or of the file. The file has not changed since the first commit of the repository, on 7 October 2026.

Plan the mock

code · task statements 1.4, 1.6

Overview · 30 seconds

Code plans all 60 questions before a model writes one

Before a model writes a question, code makes the plan of the mock: a list of 60 slots. Each slot says what one question must be: the scenario, the task statement, one point, the question type and the number of answers. The counts of a mock must hold each time, and a model that makes the plan can make an error in a count.

Explanation

3 minutes

The counts. A mock has 4 scenarios of 15 questions, and 16, 11, 12, 12, 9 questions for domains 1 to 5. The weights of the guide give the domain counts. Each slot gets one point of its task statement. An idea is a group of points of the guide on one subject: the build put the 240 points into 95 ideas. No two slots of one mock get points of the same idea.

The task statements that step 1 uses

Task statement 1.4 Implement multi-step workflows with enforcement and handoff patterns Exam guide breakdown 1.4 →
Task statement 1.6 Design task decomposition strategies for complex workflows Exam guide breakdown 1.6 →

Depth

what went wrong, and the fix

Mock 1 repeated itself, so the plan learned the ideas

Mock 1 had questions that repeated each other. Most repeats came from two points of the guide on one idea. So the build grouped the 240 points into 95 ideas, and code now stops a plan with two slots on one idea. The plan is code, so code can prevent this before any question is written.

The first version of the rule could never make a plan: a script ran it over 2000 seeds, and each seed failed. The fix gave a task statement no more questions than its number of ideas. “So the count must follow the groups, not the groups the count.” An independent review of that code then found a bug: the code could stop although a plan existed.

Mock 2 repeated mock 1

Before mock 2, the owner asked: “Is there no simple way to ensure that similar questions are spread out between mocks?” So step 1 reads the built earlier mocks, and it puts the least-used ideas first. That spread the ideas, but it did not prevent the same question in two mocks. A second review found that 17 questions of mock 2 repeat mock 1. Part of the cause was in step 1: 7 slots of mock 2 had the same point as mock 1, although their idea had a point that mock 1 did not use. So now inside an idea, the point that earlier mocks used less comes first. Step 2 got the earlier questions on the idea, and step 4 got rule B9. Over the 5 built mocks, 84 of the 95 ideas are in 2 to 4 mocks.

Write the question

a Claude model · task statements 4.3, 4.2, 4.1, 1.4

Overview · 30 seconds

One new Claude call writes each question, from a request that code builds

For each slot of the plan, one call of the Claude API writes one question. The call is new each time, and it does not know the other questions of the mock. One call makes one record, so each later verdict connects to exactly one question, and a failed try is written again alone. Code builds the request from the guide records and the plan, and code, not the model, mixes the options and gives the letters.

Explanation

3 minutes

The rules come first. From mock 4, the list of rules is a separate first block, cached, so a repeated list costs less (mock decision 0067). Today the writer gets the 21 rules that steps 3 and 4 check, so each of them is also checked. Two other instructions to the writer have no check. Each of the 488 tries of the 5 mocks used Claude Opus 5.5.

Beyond the exam

The cached block of rules. The exam tests only that prompt caching exists.

The form. The writer answers in a fixed form: the question, and each option as correct or wrong, with a reason. It can also answer “cannot write”. Claude Opus 5.5, the model of this build, and three other current models (Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1) reject a forced tool call, so the build sends its form as structured outputs. For the exam: the guide's answer for a fixed form is tool use with a JSON schema (4.3-K1). It names tool_choice "any" when several schemas exist and the document type is unknown (4.3-S2), and a forced tool when one extraction must run first (4.3-S3).

The letters. In the 12 sample questions of the guide, the correct answer is A 10 times and B 2 times, and a model can copy that (an assumption, not checked). So code mixes the options and gives the letters. The mix alone did not balance the letters (see step 8). From mock 5, the correct options take the letters that the plan sets.

The cost of one call per slot. The writer sees one slot, so it cannot see the other questions of its scenario. Step 6 checks the questions of a scenario together.

Depth

what went wrong, and the fix

The writer did not know the earlier mocks

In mock 2, the writer did not know mock 1. On a shared idea it wrote the most obvious scene again, often with the same wrong options. Example on one idea, the stop of an agentic loop:

  1. Mock 1, M1-S28: the correct answer checks the stop reason and continues while Claude asks for a tool.
  2. Mock 2, M2-S08, try 1: the correct answer again continues while Claude asks for a tool.

The owner sent it back: “Use a different scene and a different angle: the cause, the fix, or a choice between rules.” The new try asked for the cause instead: a fixed cap of 12 iterations as the main stopping rule.

The fix for step 2: when the idea of a slot is in an earlier mock, the writer gets the earlier questions on that idea, with the answer key of each. In the same mock decision, step 4 got rule B9 to check it.

In a test, a bad mark became an instruction and a check

In the first test of the writer, the owner marked one question bad: “The question is confusing and needs calrification. I had to read the question more than one time.” The assistant first suggested an instruction only. The owner asked: “but is that enough? Only in the prompt?” So the writer got the instruction “Use one name for one actor”, and because of that question, step 4 got rule B7 to check it.

The design forced a tool call

The first design said that the request forces the model to call a tool. Before the code was written, the documentation showed that the newest models reject it. So the build chose structured outputs: a JSON schema in each request. The code never had a forced tool call, and a test checks that the shared model call sends no tool and no tool choice.

Check by code

code · task statements 1.4, 4.3, 4.4, 5.3

Overview · 30 seconds

Code checks 12 exact rules before a model checks the question

Today code checks each try against 12 rules that have one exact answer, such as the number of options and the length of the text. Code runs before step 4, so a try with a simple defect does not use a step 4 model call. In mocks 1 to 5, 477 of 488 tries passed, and 11 failed.

Explanation

3 minutes

Code or a model. Code checks a rule that has one correct answer, and a model checks a rule that needs judgment.

Why the form does not count. The design never relied on the form of the writer for a count: step 3 counts the options and the correct answers. The writer is told the number of options in words only. Later, the documentation showed that a JSON schema for structured outputs cannot limit the number of items in a list, beyond a minimum of 0 or 1.

Beyond the exam

The limit of a list in a JSON schema. The exam guide does not name this limit of the API.

what went wrong, and the fix

The writer wrote 6 options for a slot of 5

Twice the writer was told to write 5 options and wrote 6: M4-S27-T3 and M5-S60-T2. In M4-S27, try 3, the sixth option was F. The form could not stop it. Rule A2 failed both tries. For M5-S60 the writer tried again by itself. M4-S27 had reached its third try, so the slot waited for the owner, who gave more tries: “The last try failed on the form (rules A1 and A2), not on B9.”

The longest option was too often correct

In the built mock 1, the correct option was the longest in 37 of the 52 one-answer questions. Chance is 13. Each question passed rule A7, which looks at one question only. The build did not choose a rule that the correct option is never the longest: then a participant learns that the longest option is always wrong. Instead, a participant who always selects the longest option must not gain from it. So from mock 2, step 1 lets the longest option be correct on 13 of the 52 one-answer slots and 3 of the 8 two-answer slots, and on each other slot, rule A12 fails a question where a correct option is as long as or longer than each wrong option.

Check by a model

two Claude model calls, then code makes the verdict · task statements 4.6, 4.3, 4.1, 1.4

Overview · 30 seconds

Two new Claude calls: one answers blind, one checks 9 rules, and code decides

Call 4a answers the question with no answer key. Today call 4b checks the 9 rules B1 to B9 with the key. Code compares the letters of call 4a with the answer key. Code also searches the feature names in the guide records, and makes the verdict. A model does not make the verdict. In mocks 1 to 5, 329 of 477 checks passed.

Explanation

3 minutes

Why two calls. Two calls with code between them make sure that the blind answer always comes first. The guide says that prompt instructions alone have a non-zero failure rate (1.4-K2). So code enforces the order, not an instruction.

Why a new call. The checker is a new call, not the writer. The guide says that review instances without prior reasoning context catch more than self-review (4.6-K2). A limit: only call 4a is blind. Call 4b gets the reasons that the writer gave.

A rule in code. For rule B6, the model lists each feature name, and code searches it in the guide records. A name that is not there fails the question.

what went wrong, and the fix
Beyond the exam

The exam tests only that prompt caching exists.

Prompt caching was missed, and added before mock 4

The first design did not use prompt caching. Each check call sent the full text of the guide again, at the full input price. Before mock 4, the owner asked if the program uses prompt caching. The assistant said no. The fix puts the guide first, the same in each call, and caches it. A 5-minute cache write costs 1.25 times the input price. On Claude Opus 5.5, a read from the cache costs 0.05 times the input price. A test on 10 questions cost $0.58 with caching. The same tokens would cost $1.72 with no cache, at the prices in the code. 2 of the 10 verdicts changed from pass to fail. A check of those 2 with no cache passed both, and the cause was not separated. The owner did not choose the Message Batches API: the rounds of the mock builder would wait for each batch.

In the exam: the guide teaches the Message Batches API to save cost (4.5-K1), and says that batch processing is inappropriate for blocking workflows.

The blind answer never caught a question

In the 477 checks of mocks 1 to 5, call 4a never selected other letters than the answer key, and never said “cannot decide”. Both B1 findings came from call 4b. Before mock 1, a test gave call 4a the 12 sample questions of the guide, and it answered 12 of 12 right. All of them have one correct answer, so the test did not cover two-answer questions.

Try again

a Claude model: the writer of step 2 again, with the failed try and its findings · task statements 4.4, 1.1, 4.3

Overview · 30 seconds

A failed try goes back to the writer with its findings

A try that fails step 3 or step 4 goes back to the writer, with its exact findings. The new try goes through steps 3 and 4 again. This is the one automatic loop of the mock builder. A try that passes stops the loop.

Explanation

3 minutes
