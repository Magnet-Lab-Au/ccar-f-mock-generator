Exam guide breakdown

The CCAR-F exam guide, broken down into its 5 domains and 30 task statements. Each task statement opens in three levels: a short answer, an explanation with the guide’s own text, and facts beyond the exam.

The exam guide on one page

The exam guide is the official reference for the CCAR-F exam: it lists the domains and the task statements that the exam tests. The exam has 60 questions, and each question states how many answers to select. Each exam uses 4 of the 6 scenarios of the guide.

How we broke it down

The guide gives each task statement two lists of points: “Knowledge of” and “Skills in”. The guide has 30 task statements with 240 points: 113 Knowledge of and 127 Skills in.

K = Knowledge ofS = Skills in1.1-K2 = domain 1 · task statement 1.1 · Knowledge of, point 2. The labels are ours. The guide has no labels.

Each task statement opens in three levels: the Overview (about 30 seconds), the Explanation (about 3 minutes), with the guide’s own text and what the exam tests, and the Depth, with facts beyond the exam, code in popups, and the steps of the mock builder (the program that wrote the mocks of this academy, see tab 2) that use the task statement.

1.1

The loop runs while Claude asks for tools

Overview · 30 seconds

“Design and implement agentic loops for autonomous task execution”

Your code sends a request to Claude and checks stop_reason. "tool_use": run the tool and send the result back. "end_turn": stop.

Explanation

3 minutes

Who decides. The guide makes a distinction. In model-driven decision-making, Claude reasons about which tool to call next, from the context. The other side is a decision tree or a sequence of tools that somebody sets up in advance. The memory of the loop: your code adds each tool result to the conversation history. That is how Claude can use the new information when it decides the next action.

The exam tests

The guide lists this topic as tested: “Agentic loop implementation: control flow based on stop_reason, tool result handling, loop termination conditions”. Under the Claude API, its list of technologies names “stop_reason values ("tool_use", "end_turn")”.

Of the 300 questions in the 5 mocks of this academy, 10 test its points.

1.2

The coordinator splits the work and routes every result

Overview · 30 seconds

“Orchestrate multi-agent systems with coordinator-subagent patterns”

A coordinator agent splits the task, calls only the subagents that the query needs, and is the only path between them. Each subagent starts without the conversation of the coordinator, so a split that is too narrow leaves gaps that no subagent can see.

Explanation

3 minutes

The hub. The guide routes all communication of the subagents through the coordinator, for observability, one way to handle errors, and control of the information (1.2-S4). In the documentation too, the main agent manages all work of its subagents, and only the final message of a subagent returns to it.

Isolated context. A subagent does not get the conversation history of the coordinator (1.2-K2). Part 1.3 shows what the coordinator must pass.

Choose the subagents. The coordinator splits the task, delegates, joins the results, and decides which subagents a query needs (1.2-K3). A sample prompt in the documentation also tells Claude to use one subagent, not several, when one is enough (1.2-S1).

Split the scope. The guide gives each subagent a distinct subtopic or source type, so that the work does not repeat (1.2-S2). A split that is too narrow leaves parts of a broad topic with no coverage (1.2-K4). In sample question 7 of the guide, each subagent did its task correctly. The problem was what they were given.

Refine. The coordinator checks the synthesis for gaps, sends targeted queries to the search and analysis subagents, and runs the synthesis again, until the coverage is sufficient (1.2-S3). Only the guide describes this loop.

1.3

A subagent sees none of the coordinator's conversation

Overview · 30 seconds

“Configure subagent invocation, context passing, and spawning”

A coordinator starts each subagent with a call of the Task tool. The subagent does not see the conversation of the coordinator, so the prompt of the call must hold the complete findings and their sources.

Explanation

3 minutes

Spawn. The guide: a coordinator starts a subagent with the Task tool, and its allowedTools must include “Task”. The product renamed the tool Agent in version 2.1.63. In the current Agent SDK, allowed_tools (allowedTools in the guide) only approves a tool in advance. The Agent tool runs even when the list does not name it. The exam uses the guide.

Context. Only the prompt of the tool call goes from the coordinator to a subagent. The subagent does not get the conversation history or the tool results of the parent. Only the final message of the subagent goes back. So the coordinator puts the complete findings of earlier agents in the prompt (1.3-S1), and keeps the content apart from its metadata, such as the source URL, to keep the attribution (1.3-S2). The documentation also separates the content and the source of a document.

Definitions. An AgentDefinition gives each type of subagent a description, a system prompt and a list of tools (1.3-K3). Claude chooses a subagent by its description. A tool that the list leaves out is not in its session.

Parallel. One response of Claude can hold several tool calls. So the coordinator starts parallel subagents with several Task calls in one response, not across separate turns (1.3-S3). Subagents can run at the same time.

Goals, not steps. A coordinator prompt gives research goals and quality criteria, not step-by-step procedures, so that a subagent can adapt (1.3-S4). The documentation also asks for clear success criteria.

Fork. A fork of a session starts with a copy of the history. The original does not change. So two approaches can start from one shared analysis (1.3-K4). Part 1.7 explains sessions.

The exam tests

Among the technologies, the guide names “Claude Agent SDK — agent definitions, agentic loops, stop_reason handling, hooks (PostToolUse, tool call interception), subagent spawning via Task tool, allowedTools configuration”. Among the topics: “Subagent context management: explicit context passing, structured state persistence, crash recovery using manifests”. Of the 300 questions in the 5 mocks of this academy, 12 test its points.

1.4

A required order needs a code gate, not a prompt

Overview · 30 seconds

“Implement multi-step workflows with enforcement and handoff patterns”

When a step must come first, such as identity verification before a refund, code blocks the later tool call until the step is done, because a prompt instruction can fail. When the agent escalates, it gives the human a structured summary, because the human does not see the conversation.

Explanation

3 minutes

Code or prompt. The guide separates enforcement by code, such as hooks and prerequisite gates, from guidance in a prompt (1.4-K1). The documentation says the same: Claude treats its instructions as context, not as enforced configuration. To block an action whatever Claude decides, use a PreToolUse hook.

A prompt can fail. When compliance must be certain, such as identity verification before a financial operation, a prompt alone has a failure rate above zero (1.4-K2). Sample question 1 of the guide gives the reason: code gives a guarantee, a prompt gives only a probability.

The gate. Code blocks process_refund until get_customer has returned a verified customer ID (1.4-S1). In the Agent SDK, a PreToolUse hook gets each tool call before it runs, and can block it. It sees one call: whether get_customer has returned an ID is state that your code keeps. A deny carries a reason, so the model knows why and can call get_customer first.

Many concerns. A request with several issues becomes distinct items. The agent investigates each one, then joins them in one resolution (1.4-S2). The guide says “using shared context”. In the documentation, agents that work in parallel have their own isolated context. The exam uses the guide.

The handoff. When the agent escalates, it writes a structured summary: customer ID, root cause, refund amount and recommended action, because the human does not see the transcript (1.4-K3, 1.4-S3). Only the guide describes the content of a handoff.

1.5

Hooks block a tool call or clean its result

Overview · 30 seconds

“Apply Agent SDK hooks for tool call interception and data normalization”

A hook is your code at a fixed point of each tool call. Before the call, it can block it. After the call, it can replace the result before Claude sees it. So code, not the model, enforces a rule and cleans the data.

Explanation

3 minutes

Before the call. A hook intercepts an outgoing tool call to enforce a rule, such as no refund above a threshold (1.5-K2). In the Agent SDK, a PreToolUse hook that rejects a call stops it, and Claude gets the rejection message instead. In the guide, the hook then redirects the case, for example to a human (1.5-S2). The documentation has no redirect field: a deny gives Claude its reason (see 1.4). A hook can also answer “ask”, to ask the user. The exam uses the guide.

After the call. A PostToolUse hook makes the data of different MCP (Model Context Protocol) tools the same, such as Unix timestamps, ISO 8601 dates and numeric status codes, before the agent uses it (1.5-K1, 1.5-S1). The field updatedToolOutput replaces the output before Claude sees it, for any tool, not only MCP tools. The exam uses the guide. A matcher, a pattern of tool names, selects the tools, for example each MCP tool.

A guarantee. The guide contrasts the deterministic guarantee of a hook with the probable compliance of a prompt (1.5-K3, 1.5-S3). Part 1.4 explains this contrast. A deny of a hook holds in each permission mode, also in the mode that skips all approvals.

The exam tests

Depth

Beyond the exam

The exam tests the points of the guide above. These facts of the documentation go further, for work in production.

  • A PostToolUse hook cannot undo an action: the tool has already run. So a refund limit belongs in a PreToolUse hook.
  • MCP output that a hook replaces gets no schema check, and a hook that removes error details can mislead Claude.
  • Claude Code also has prompt hooks, which ask a model. Only a hook that is code is deterministic.
  • A PostToolUse hook that times out does not stop the turn: Claude gets the original result. So a slow normalizer lets the raw data through.

Explanation

3 minutes

Scope by role. Each subagent gets only the tools of its role, so that it does not misuse tools of another role, such as a synthesis agent that searches the web (2.3-K2, 2.3-S1). The documentation gives its own reason: fewer tools reduce the risk of unintended actions. A tool that the list of a subagent leaves out is not in its session.

Narrow tools. A generic tool becomes a constrained one, such as load_document that checks document URLs, in place of fetch_url (2.3-S2). A narrow tool of another role serves a frequent need, and complex cases still go through the coordinator (2.3-S3). Only the guide describes these two points.

tool_choice. The guide names three options: auto, any, and a forced tool (2.3-K4). With any, Claude must call a tool and gives no text (2.3-S5). A forced tool makes one tool run first, and the next steps follow in later turns (2.3-S4). The documentation names four: it adds none, which blocks all tools. Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 return a 400 error for any and for a forced tool. The exam uses the guide. The mock builder follows the documentation (step 2 of tab 2).

Share MCP servers in .mcp.json, with secrets in variables

Overview · 30 seconds

“Integrate MCP servers into Claude Code and agent workflows”

A team commits its shared MCP servers in .mcp.json and writes each token as an environment variable. A person keeps private servers in ~/.claude.json. The agent gets the tools of all servers together, and resources show it what data exists before it searches.

Explanation

3 minutes

Two files. The team commits .mcp.json, so that each member gets the same MCP servers (2.4-S1). User scope is in ~/.claude.json, for all the projects of one person (2.4-S2). The documentation has a third scope: local, the default, also in ~/.claude.json, which it names for experimental servers. The exam uses the guide.

Secrets. In .mcp.json, a token is a variable such as ${GITHUB_TOKEN}, so the secret is never committed (2.4-K2). Claude Code expands the variable when it loads the file, so a team shares the file and each person keeps the key.

All tools at once. Each tool name carries the name of its server, so the tools of many servers can sit side by side. The guide says that the tools are discovered at connection time. In Claude Code, by default, only the tool names load at the start, and the full definitions load on demand. The exam uses the guide.

Resources. A server can expose a catalog, such as issue summaries or database schemas, as resources, so the agent sees what data exists without exploratory tool calls (2.4-K4, 2.4-S5). Claude Code gives Claude tools to list and read them.

Good servers. A detailed description of an MCP tool keeps the agent from using a built-in tool such as Grep in its place (2.4-S3). Part 2.1 shows how. For a standard integration such as Jira, the guide uses an existing community server, and a custom server only for a workflow of the team (2.4-S4). The documentation warns: check that you trust each server before you connect it.
