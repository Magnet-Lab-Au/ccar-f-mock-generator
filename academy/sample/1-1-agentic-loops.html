“Design and implement agentic loops for autonomous task execution”

Explanation3 minutes

In plain words

The loop. Your code sends a request to Claude and looks at stop_reason in the response. "tool_use" means that Claude wants a tool. Your code runs the tool and sends the result back for the next iteration. When it is "end_turn", your code stops the loop.

The memory of the loop. Your code adds each tool result to the conversation history. That is how Claude can use the new information when it decides the next action.

Who decides. The guide makes a distinction. In model-driven decision-making, Claude reasons about which tool to call next, from the context. The other side is a decision tree or a sequence of tools that somebody sets up in advance.

Three wrong ways to stop. The guide names three anti-patterns:

✗ Read the wordsParse natural language signals to decide when the loop ends.
✗ Count to a limitMake an arbitrary limit of iterations the main way to stop.
✗ Look for textTreat text from the assistant as the sign that the work is complete.
✓ Check the fieldContinue on "tool_use". Stop on "end_turn".

A loop that stops when the work is right

How the mock builder uses the idea of task statement 1.1

Overview30 seconds

The mock builder is not an agentic loop. Code and the owner decide each next step. No model decides it. The builder has one automatic loop for questions: a question that fails a check goes back to the writer. The main way to stop is a pass. The limits are only guards.

The story3 minutes

Why the builder does not need an agentic loop

The work of a mock is known before it starts. Before a model writes any question, code makes a plan of 60 slots. Each slot says what one question must be. So code follows a fixed sequence of steps. That is the other side of the distinction in 1.1-K3: no model decides what happens next.

The one loop

A question that fails the check by code or the check by a model goes back to the writer with the exact findings, and the writer tries again. The loop stops when a question passes both checks. A limit of 3 tries and a limit of two results "cannot decide" are only guards. After a guard, the slot waits for the owner.

This matches 1.1-S3: an arbitrary limit of iterations must not be the main way to stop. The guide wrote that point for agentic loops. The builder uses the same idea for a loop of retries.

What happened in mock 1

Mock 1 needed 83 tries for 60 slots. 9 of the tries were rewrites that the owner asked for after the marks. 18 slots needed more than one try: 11 after a failed check, and 7 only after a rewrite that the owner asked for. One slot stopped at the guard, and the owner gave it more tries.

What went wrong, and the fix

The first design had many automatic paths for repair. A first review found 14 serious items. A second review found 10 new ones, and most of them came from the answers to the first. The owner said: “I suspect that if we fix these new 10 issues and review we will keep finding more and the cycle will continue.”

The fix: one automatic loop, and each other failure waits for the owner. The control became code, with tests that make no model call.
