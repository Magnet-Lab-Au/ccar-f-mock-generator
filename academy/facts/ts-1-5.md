## 2. The takeaway

**Proposed heading (8 words):** "A hook guarantees what a prompt can only request"

**Short answer:** A PreToolUse hook checks each tool call before it runs and can block it. A PostToolUse hook can replace each tool result before Claude sees it, so code, not the model, enforces a business rule and cleans the data.

Support: F2, F4, F6 and F9 (the two hook events), F11 and F12 (deterministic against the model choice). The heading is a claim of the guide (GUIDE 186, 192). The documentation supports it for code hooks only (conflict C2).

## 5. Beyond the exam

1. **PostToolUse cannot undo the action.** HOOKS-REF 2189: "`updatedToolOutput` only changes what Claude sees. The tool has already run by the time the hook fires, so any files written, commands executed, or network requests sent have already taken effect." HOOKS-GUIDE 961: "`PostToolUse` hooks can't undo actions since the tool has already executed." So a refund rule must be a PreToolUse hook. A PostToolUse hook is too late. The guide does not say this.
2. **A bad replacement is ignored, or misleads.** HOOKS-REF 2191: "For built-in tools, a value that doesn't match the tool's output schema is ignored and the original output is used. MCP tool output is passed through without schema validation. Stripping error details that Claude needs can cause it to proceed on a false assumption." For S1, the normalizer of MCP output gets no safety check from the SDK.
3. **A hook that times out.** SDK-HOOKS 793: "`PreToolUse`: Claude Code doesn't run the tool call, Claude receives a tool result stating the hook didn't respond before its timeout, and the turn continues." SDK-HOOKS 794: "`PostToolUse` and `PostToolUseFailure`: Claude Code keeps the tool result and the turn continues." So a slow normalizer lets the raw data through. Marked: this differs from "deterministic" in the guide (C2).

  async def block_etc_writes(input_data, tool_use_id, context):
      file_path = input_data["tool_input"].get("file_path", "")

      if file_path.startswith("/etc"):
          return {
              # Top-level field: message shown to the user

## 9. Conflicts

- **C1. The name of the interception hook.** GUIDE 185 and 191 say "intercept outgoing tool calls" and "tool call interception hooks". The guide names no event for it. The documentation event is `PreToolUse` (SDK-HOOKS 149). The exam uses the guide words.
- **C2. "Deterministic" is true for code hooks only.** GUIDE 186 says hooks give "deterministic guarantees". HOOKS-GUIDE 845: "For decisions that require judgment rather than deterministic rules, use `type: \"prompt\"` hooks. Instead of running a shell command, Claude Code sends your prompt and the hook's input data to a Claude model to make the decision." A prompt hook is a hook, but it is not deterministic. Also a PostToolUse hook that times out lets the original result through (SDK-HOOKS 794). The exam uses the guide: an SDK callback hook is code.
- **C3. "Redirect to alternative workflows".** GUIDE 191 says the hook redirects to "human escalation". The documentation has no redirect field. A deny stops the call and gives the reason to Claude (SDK-HOOKS 353-354). The hook can also return `"ask"` to ask the user (HOOKS-REF 1909). So the redirect is the reason text or the `ask` decision. Weak claim: the guide does not say how. The exam uses the guide.
- **C4. "From different MCP tools".** GUIDE 190 ties normalization to MCP tools. In the current documentation, `updatedToolOutput` "works for any tool in both SDKs" (SDK-HOOKS 251). The older field `updatedMCPToolOutput` was for MCP only. Both are correct for MCP tools. The exam uses the guide.
- **C5. Hooks are not in the in-scope list.** GUIDE 1017-1041 has no hook line. GUIDE 999 (technologies) names hooks. Note only.
- **C6. Weak sample question support.** No sample question has 1.5 as its main point. Question 1 tests 1.4-S1 and uses the words of 1.5-K3 (section 4).

Number of conflicts: 6 (C1 to C4 are differences of sources, C5 and C6 are weak claims).
