## 2. The takeaway

**Proposed heading (8 words):** "The description decides which tool Claude picks"

**Short answer:** Claude chooses among tools mainly by their descriptions, so each description must say what the tool does, its inputs, what it returns and when to use it instead of a similar tool. Remove overlap by renaming or splitting tools, and check the system prompt for words that pull Claude to the wrong tool.

Support: F1 to F3, F15 (the description drives the choice), F4 to F6 (its content), F7 (ambiguity), F9 and F10 (naming, splitting), F11 to F14 (the system prompt). "Keyword-sensitive" is a guide word only (C2).

## 5. Beyond the exam

1. **Claude Code cuts long MCP tool descriptions.** CC-MCP 1458: "Claude Code truncates each tool description and each server's instructions at 2,048 characters by default. Keep them concise, and put critical details near the start." Marked: the guide (GUIDE 236) gives no limit. A boundary at the end of a long description can be lost.
2. **Too many tools also break selection.** TSR 12: "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." Good descriptions do not fix this. The guide names no number of tools in 2.1.
3. **Examples of inputs have their own field.** DEF 80: "for tools with complex inputs, nested objects, or format-sensitive parameters, you can use the `input_examples` field to provide schema-validated examples." Marked: the guide puts "example queries" in the description (GUIDE 236, C3).

## 9. Conflicts

- **C1. Split or consolidate.** S3 says "Splitting generic tools into purpose-specific tools" (GUIDE 244). DEF 82 says: "**Consolidate related operations into fewer tools.** Rather than creating a separate tool for every action (`create_pr`, `review_pr`, `merge_pr`), group them into a single tool with an `action` parameter." They can agree (split a tool with different jobs, join actions on one resource), but a reader can see opposite advice. The guide itself names both in GUIDE 1024 ("splitting vs consolidating tools") and calls consolidation "a valid architectural choice" (GUIDE 764). The exam uses the guide.
- **C2. "Keyword-sensitive" is a guide claim.** No documentation page read says that one keyword in a system prompt makes an unintended tool association (K4, S4). The nearest are PBP 491 (aggressive words cause overtriggering), OV 742 (the system prompt steers tool use) and DEF 564 (prompting influences which tool `auto` picks). Weak support. The exam uses the guide.
- **C3. "Example queries" in the description.** The guide puts example queries in the description (GUIDE 236, 756). The documentation lists what the description contains (DEF 75-78) and has no example queries in that list. It gives example inputs a separate field, `input_examples` (DEF 25, 80). The exam uses the guide.
- **C4. Output contracts.** S1 and S3 ask for outputs and "input/output contracts" (GUIDE 242, 244). The tool definition table (DEF 22-25) has `name`, `description`, `input_schema` and `input_examples`, and no output field. The documentation describes the output in the description text (DEF 129: "what data it returns") and advises "Design tool responses to return only high-signal information" (DEF 86). The Tool reference page was not read (not checked).
- **C5. The tab 2 link is an analogy only.** Decision 0019 line 29 cites 2.1-S3 for step contracts. No build guide table uses 2.1, and the pipeline sends no tool (decision 0040 line 22). The page must not say that the build used 2.1.
