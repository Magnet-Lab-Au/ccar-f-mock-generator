## 2. The takeaway

**Proposed heading (10 words):** "Give each agent only the tools that its role needs"

**Short answer:** Each agent gets a small set of tools for its role, plus a narrow shared tool for a frequent need, and the coordinator handles the rest. `tool_choice` sets if Claude can, must, or must use one named tool, but the newest models reject the forced settings.

Support: F1 to F4 (few tools), F5 to F8 (scope per role), F9 and F15 (narrow cross-role tool), F10 to F14 (tool_choice and its model condition, C2).

## 5. Beyond the exam

1. **In the Agent SDK, `allowedTools` does not remove a tool.** SDK-CT 387: "`tools` and bare-name `disallowedTools` entries change availability. `allowedTools` and scoped `disallowedTools` rules change permission." SDK-PERM 76: "Any other tool not listed in `allowed_tools` is still available to Claude". To scope an agent, use `tools` or a bare-name deny. Marked: the guide names "allowedTools configuration" (GUIDE 999) and does not separate the two layers (C7).
2. **A forced call skips thinking, and a change of `tool_choice` breaks part of the cache.** DEF 866: "Forcing a tool also skips thinking on every model that accepts forced tool use: the response starts with the `tool_use` block and has no `thinking` block." DEF 853: "changes to the `tool_choice` parameter will invalidate cached message blocks." Marked: S4 changes `tool_choice` between turns (GUIDE 283) and names no cost.
3. **At scale, load tools on demand.** TSR 12: "Because tool search loads only a focused set of relevant tools on demand, selection accuracy stays high even across thousands of tools." Condition: TSR 14 refers to a list of models that support tool search (not checked for each model). The guide (K1) only reduces the number of tools.

## 9. Conflicts

- **C1. The number of tools.** K1 says 18 tools are too many and 4-5 are right (GUIDE 270). TSR 12 puts the drop at "30–50 available tools". No page read says that 18 tools degrade the selection. TSR 11 names "3–5 tools" for one request, close to the guide. The exam uses the guide.
- **C2. Forced tool use is model-dependent.** K4, S4 and S5 present `any` and forced selection with no condition (GUIDE 273, 283, 284). DEF 564: on Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1, "`any` and `tool` return a" 400 error. DEF 563: manual extended thinking also rejects them. PAR 1134 repeats the model list. The exam uses the guide. The build follows the documentation (decision 0040).
- **C3. "Guarantee" a tool call (S5).** On the four models of C2, no API setting guarantees a tool call. The replacement that DEF 564 names, "`auto` with" strict tool use, guarantees "schema-valid tool inputs", not a call, and "Prompting still influences which tool `auto` picks." OV 744 says "To require a tool call rather than rely on prompting, set" `tool_choice`, with no model condition. That line is weak for the newest models.
- **C4. Three options or four.** The guide names "auto", "any" and forced (GUIDE 273, 1006). DEF 845-850 names four and adds `none`.
- **C5. Misuse (K2) is a guide claim.** No page read says that an agent "tends to misuse" tools outside its role. The documentation gives other reasons: "reducing the risk of unintended actions" (SDK-SUB 29) and "security and focus" (CC-SUB 1233). Weak support.
- **C6. Split against consolidate.** DEF 82 says "Consolidate related operations into fewer tools." S2 replaces a generic tool with a constrained one (GUIDE 278). These can agree (the aim is a smaller, safer surface), but a reader can see opposite advice. The exam uses the guide.
- **C7. `allowedTools` is not a scope.** GUIDE 999 and 724 name `allowedTools`. SDK-PERM 76 and SDK-CT 387 say that it changes permission, not availability. An answer that scopes a subagent by `allowedTools` alone is wrong in the SDK. Not tested in 2.3 directly.
- **C8. Source condition.** MAO (F4) is a Managed Agents page with "status: beta" (MAO 9), not the Agent SDK of the guide scenario.
