## 2. The takeaway

**Proposed heading (10 words):** "Pin exact facts outside the summary, and trim the rest"

**Short answer:** A summary of a long conversation blurs numbers, dates and promises, so keep these facts in a separate block that each request carries word for word. Send the full history each time, but cut tool results and agent outputs to the fields that the next step needs.

Support: F1 to F6 (K1, S1, S2), F9 to F11 (K4), F12 to F16 (K3, S3), F17 to F19 (S5, S6).

## 9. Conflicts

- **C1. K2 has weak documentation support.** No saved page uses the words "lost in the middle" (grep of `academy/sources/`). CW 11 names "context rot": accuracy falls as the count of tokens grows. That is about length, not about position. The exam uses the guide.
- **C2. S4 and the documentation put different things first.** S4: key findings summaries "at the beginning of aggregated inputs" (GUIDE 556). CPB 246, 249: long documents at the top, the query at the end. These do not contradict, because a short summary can go first in the data block. But a reader can confuse "put the data first" with "put the findings first". The exam uses the guide.
- **C3. K4 says "complete" history.** WWM 161 agrees: the API is stateless. But the documentation also replaces old turns with a summary (COD 36) and clears old tool results (CE 40). So in production the history is often not complete word for word. S1 assumes this too ("outside summarized history"). Read K4 as "send the history again each time, because the API keeps none".
- **C4. S3 and context editing work at different points.** S3 cuts fields of each tool result before it enters the context. Context editing clears whole old results later (CE 40, MTC 34). The documentation form of S3 is DT 86 (design of the tool) or SHOOK 251 (a hook, Agent SDK).
- **C5. Two Claude Code pages differ in tone.** BP 384: compaction "preserves important code and decisions while freeing space". HCW 121: "instructions from early in the conversation can get lost". The second agrees with K1.
